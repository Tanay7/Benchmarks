### 1.4 Jumper caps ("short-circuit bubbles")

| Cap | Where it sits | What it does | Evidence |
|---|---|---|---|
| **M1 cap** | across header pin **7 (M1)** and pin **8 (GND)** | fitted: M1 = 0; removed: M1 = 1 | p.8 mode-0 figure (two caps on the four right-most bottom pins); p.9 "WOR Mode (Mode 1, remove M0 short-circuit bubble)" figure keeps only the **left** cap (7-8) |
| **M0 cap** | across header pin **9 (GND)** and pin **10 (M0)** | fitted: M0 = 0; removed: M0 = 1 | p.9 "Configuration Mode (Mode 2, remove M1 short-circuit bubble)" figure keeps only the **right** cap (9-10) |
| **RXD cap**, **TXD cap** | a 2 x 2 pin block labelled RXD / TXD beside the USB-C socket | not described anywhere in the text (**not found**). Inference: they bridge the USB-UART's lines to the module's UART. Basis: the USB port is "a communication interface between a PC and the module" (p.6 item 6) and the header pins are the module's own pins (p.4 §1.1, p.6 item 2), so the caps are the only element between the USB-UART and the module. VERIFY by continuity (section 12) | Fig. 1 p.4, Fig. 2 p.5, all mode figures p.8-10 |

* The board's M0/M1 caps carry **no M0/M1 label of their own**: they are ordinary jumper caps
  across a signal pin and its neighbouring GND pin on the bottom header.
* A removed cap leaves the pin to the module's **"very weak pull-up"** (T37S §3 pins 9/10, p.8).
  Whether the TBH-02 adds pull-ups of its own: not found.
* Mode by caps (TBH §3 p.8-10, consistent with T37S §6 p.14): both fitted = mode 0 normal; M0
  cap removed = mode 1 WOR; **M1 cap removed = mode 2 configuration**; both removed = mode 3
  deep sleep.
* As shipped/rendered, all four caps are fitted (Fig. 1, Fig. 2, p.8 mode-0 figure).
* The hero render Fig. 1 (p.4) shows caps in positions used nowhere else, including one
  **across top-header pins 11-12 (3.3V-GND)** and one at the GND end of the bottom header. This
  contradicts the pin table (pin 11 "hovering") and the mode figures. Never copy that render.

## 2 E22-400T37S module: extracted facts

### 2.1 Supply and logic level

### 2.3 Pins of the module

28 edge pins + matrix pad 29 (T37S §3 p.7-8). M0 and M1: "Input (very weak pull-up)", "not
floating, if not used, it can be grounded". AUX output; RESET input ("Module reset pin"); STATE
output; 485-EN I/O; 3.3V "just leave it in the air". Pad 29: "Users need to ground them to assist
in the heat dissipation of the module".

### 2.4 Working modes and switching

| Mode | M1 | M0 | Function | Source |
|---|---|---|---|---|
| 0 Transfer (normal) | 0 | 0 | serial open, wireless open, transparent; "Support special command air configuration" | T37S §6 p.14, §6.2 p.15 |
| 1 WOR | 0 | 1 | WOR sender / receiver | §6, §6.3 |
| 2 Configuration | 1 | 0 | registers accessible; wireless TX and RX off | §6, §6.4 |
| 3 Deep sleep | 1 | 1 | no TX, no RX; leaving it reconfigures the parameters with AUX low | §6, §6.5 |

Switching (T37S §6.1 p.14): idle module works in the new mode after 1 ms; with pending data the
switch waits until the data is processed; "mode switching is only effective when AUX output is 1,
otherwise the switching will be delayed"; recommendation: "detect the output status of the AUX
pin and wait for 2ms after the output is high before switching". §5.6.4 note 3: the new mode is
entered "at least 2ms after the AUX rising edge".

### 2.5 AUX

* Power-on: "AUX will immediately output a low level, perform a hardware self-check ... After
  completion, AUX outputs a high level ... the user needs to wait for the AUX rising edge"
  (§5.5 p.11). The self-check also runs on "instruction reset and exit mode 3" (§5.6 timing
  figure p.13). Self-test duration: not found.
* AUX low while the 1000-byte buffer is not empty; "When AUX=1, it does not mean that all serial
  port data of the module has been transmitted wirelessly. It is also possible that the last
  packet of data is being transmitted" (§5.6.2 p.12).
* AUX goes low 2-3 ms before received data leaves TXD ("To wake up the external MCU 2-3ms in
  advance", §5.6.1 timing figure p.12).
* Low has priority; while low, no mode detection (§5.6.4 notes 1-2 p.12).

### 2.6 RESET and STATE

* RESET: "Module reset pin" only (§3). The §4 diagram puts an RC (resistor to "VCC", capacitor to
  GND) on it, driven by MCU IO4. Whether the module has an internal pull-up: not found.
* STATE: flashes / flips level per abnormal state (§5.7 p.13). Electrical level: not found.

### 2.7 Abnormal-status log (T37S §5.7 p.13)

| Abnormal state | Threshold | STATE indicator | UART log |
|---|---|---|---|
| Under-voltage | supply < 4.5 V | flash once every 500 ms / level flip | `FF FF FF 01` |
| Over-voltage ("Overpressure") | supply > 15 V | once every 1 s | `FF FF FF 02` |
| Over-temperature | module temperature > 120 C | once every 2 s | `FF FF FF 03` |
| Over-voltage and over-temperature | both | always on | `FF FF FF 04` |

"The module will temporarily shut down the RF transmission function when it is in an abnormal
working state, and will restart the transmission after it returns to normal"; the log is printed
"every 500ms (can be turned on/off)"; enable bit = REG1 (04H) bit 2, "default value is 0
(disabled)". There is no code for under-voltage + over-temperature.

### 2.8 Configuration protocol and registers (T37S §7 p.16-20)

* Mode 2 only, "only 9600, 8N1 format is supported" (§7.1).
* `C0 addr len data` write and save; `C1 addr len` read; `C2 addr len data` write temporary;
  `CF CF` + instruction = wireless configuration; `FF FF FF` = format error (§7.1). Product
  information 80H-86H, 7 bytes, read only (§7.2 p.20). CRYPT 07H/08H "Write only, read returns 0".
* REG0 03H: UART [7:5] (011 = 9600 default), parity [4:3], air rate [2:0].
* REG1 04H: sub-packet [7:6] (00 = 240), [5] ambient-noise RSSI enable ("send instructions C0 C1 C2
  C3 in transfer mode or WOR send mode", registers 00H noise, 01H last RSSI, dBm = -(256 - RSSI)),
  [4:3] reserved, [2] abnormal-log enable, [1:0] power (all 37 dBm).
* REG2 05H channel. REG3 06H: [7] RSSI byte appended, [6] fixed-point, [5] relay, [4] LBT (max 2 s
  wait), [3] WOR role, [2:0] WOR cycle (1 + code) x 500 ms.
* Factory defaults: 433.125 MHz, address 0x0000, channel 0x17, 2.4 kbit/s, 9600 8N1, 37 dBm
  (§7.3 p.20). Parameters survive power-off (§1.2 p.5).

### 2.9 Thermal and duty cycle

* Built-in over-temperature protection "will automatically stop sending when the maximum
  temperature of the module is exceeded" (§1.2 p.5); threshold > 120 C (§5.7).
* Operating -40..+85 C (§2.1, §2.2).
* Matrix pad for heat dissipation (§1.2 p.5; §3 pin 29).
* **Duty-cycle limit: not found** (the words "duty" and "continuous transmission" do not occur in
  the T37S manual or the TBH-02 manual). Thermal resistance: not found.

## 6 Correct interfacing (a): spacecraft UNO Q (ABX00162 or ABX00173)

### 6.1 What to remove / leave

| Item | Action | Why |
|---|---|---|
| M1 cap (pins 7-8) | **remove** | the UNO Q drives M1 (D3); a cap would short D3 to GND when driven HIGH |
| M0 cap (pins 9-10) | **remove** | same for D2 |
| RXD and TXD caps (2 x 2 block by the USB-C) | **remove** | they tie the CH340X to the module UART that the UNO Q drives (inference section 1.4); `config.h:84-85` |
| TBH-02 USB-C | **leave unplugged** | not used in flight; avoids a second UART driver and a USB ground path |
| Keep the four caps | store them | needed again for ground use or PC configuration |

### 6.2 Signal wiring (female jumper wires onto the TBH-02 bottom header)

|---|---|---|---|---|---|

Levels: module UART and control pins are 3.3 V logic (T37S §2.2), the UNO Q headers are 3.3 V
(UNOQ §9.6): direct connection, no level shifter. The pull-ups go to the UNO Q's **+3V3 OUT
(JANALOG 4)**, never to the TBH-02 pin 11. With the pull-ups the module rests in mode 3 while the
MCU boots (`docs/03:277-279`); `begin()` then drives mode 3 itself, configures in mode 2 and runs
in mode 0 (`e22.cpp:49-57, 132-159`).

### 6.4 Before first power-up and checks

1. Antenna or **>= 10 W 50 Ohm dummy load** on the SMA (T37S §3 note; 37.5 dBm max = 5.6 W, T37S
   §2.2; `docs/03:867`).
2. Meter: M0 and M1 header pins read about 3.3 V to GND with the UNO Q powered and the MCU not yet
   driving them (pull-ups); pin 11 not connected; terminal polarity correct.
3. Strap wire A0-GND fitted; power on (strap read once at boot, `config.h:95`).
4. Expect EVR 0x0308 `radio model E22-400T37S (strap to GND, 5/5 low; build E22-400T33D)` and EVR
   0x0306 `... pwr 37 dBm sens -126.0 dBm datasheet` (`docs/00:870-874`), RF `radio_model` = 2.
5. The TBH-02's PWR LED lights with 12 V; the TXD_LED/RXD_LED probably sit on the CH340X side and
   may stay dark with the RXD/TXD caps removed (inference; not a fault).

### 6.5 Behaviour of the flight software with the T37S (all already coded)

REG1 = 0x24 (240-octet sub-packets, ambient-noise RSSI, abnormal-status log, power field 00)
(`radio.cpp:136-142`); every power code = 37 dBm (`radio.cpp:24`); brown-out derating has no
effect (`test_radio.cpp:408-409`); `FF FF FF 01..04` decoded into FDIR and EVR 0x0311-0x0315,
over-temperature -> transmitter off 300 s, SAFE, frame period doubled (`radio.cpp:346-351`,
`config.h:277-282`, `docs/14:288-319`); TX duty capped at 50 % for every model (project limit,
`docs/03:340`).

## 7 Correct interfacing (b): ground UNO Q 4 GB (ABX00173) through the USB-C hub

### 7.1 Topology

```
 USB-C PD charger --PD in--> [ USB-C hub / dongle with PD pass-through ] --host plug--> UNO Q USB-C
                                   | downstream port
                                   +--USB cable--> TBH-02 USB-C (CH340X)     /dev/ttyUSB*
 12 V >= 1.5 A adapter --(2 A fuse)--> TBH-02 green terminal (or DC jack)
 TBH-02 SMA --> antenna / feeder (or >= 10 W dummy load / attenuator chain)
 Option G-B only: TBH-02 header 10 M0, 7 M1, 4 AUX, 8 GND --> UNO Q headers (RCU)
```

| Fact behind it | Source |
|---|---|
| UNO Q USB-C: "USB 3.1 with Role-Switching Capabilities"; PD "requests a 5 V / 3 A contract only"; VBUS back-drive protection Q2801 | UNOQ §2.2.2, §10 |
| Arduino lists "USB-C dongle with external power delivery capabilities" as a related product and prescribes it for peripherals in SBC mode | UNOQ §2.3; §11.1 |
| "Use a supply and cable rated for 5 V at 3 A"; VBUS_USBC 4.5 / 5.0 / 5.5 V | UNOQ §3.1, §3.2 |
| Q2801 "can source USB VBUS from 5V_SYS when the board operates as a USB host/OTG" | UNOQ §4.3 |
| 4 GB variant recommended for App Lab in SBC mode | UNOQ §11.1 |
| The TBH-02's USB is a data path only; the module is powered from the jack/terminal | TBH p.6 item 6; p.8 note 2 |

USB power drawn by the TBH-02 from the hub: only its USB-side circuitry (value not found; small).
The 5 W PA never loads the hub or the UNO Q.

USB cable: if the hub's downstream port is USB-A, use a USB-A to USB-C data cable (works
regardless of the TBH-02's CC wiring). A USB-C to USB-C cable from a hub USB-C port needs the
TBH-02 to present Type-C sink resistors on CC, which is not documented (not found) - VERIFY
(section 12); fall back to an A-to-C cable if it does not enumerate.

Alternative power plan (not the owner's stated plan): feed the UNO Q VIN (JANALOG 8, 7-24 V,
UNOQ §3.1, §9.7) from the same 12 V supply (>= 3 A) and let the UNO Q source the hub's VBUS
(UNOQ §4.3); the Q2801 current limit is not published - VERIFY.

|---|---|---|
| RXD / TXD caps | **fitted** (CH340X <-> module) | **fitted** |
| M1 cap (pins 7-8), M0 cap (pins 9-10) | both **fitted** after the one-time configuration (mode 0) | both **removed** after the one-time configuration, **before** any wire goes to pins 7/10 |
| Header wiring | none | 10 M0 -> UNO Q D2 (PB3), 7 M1 -> D3 (PB0, TT 3.6 V), 4 AUX -> D4 (PA12), 8 GND -> UNO Q GND; 10 kOhm M0 and M1 to UNO Q +3V3 (JANALOG 4). Pin numbers proposed = the station sketch's `PIN_RCU_M0/M1/AUX = 2/3/4` (`sketch.ino:127`); the final assignment belongs to the v4 contract |
| Header TXD/RXD (pins 5/6) | **not connected** (the CH340X drives them through the caps) | not connected |
| `[radio] model` | `"E22-400T37S"` | same |
| `[radio] fault_log` | `true` (otherwise no `FF FF FF 0x`; `e22.py:85`) | same |
| `[radio] port` | the CH340X's `/dev/serial/by-id/...` path (stable when the E15-USB-T2 is also plugged) or `/dev/ttyUSB0` | same |

Never fit a cap and wire the RCU at the same time: `rcu_mode` drives M0/M1 HIGH for modes 1-3
(`sketch.ino:221-222`) into a pin the cap shorts to GND.

### 7.3 One-time configuration of the ground T37S (both G-A and G-B)

The ground module's factory state has the RSSI byte and the noise register off (T37S §7.2-7.3);
the GDS needs both, the abnormal log, channel 23 and 2.4k (`station.toml:59-70`).

1. Stop the ground App (it holds the port; `docs/00:638`).
2. Antenna or >= 10 W dummy load on the SMA.
3. Caps: RXD and TXD fitted; **M0 cap (pins 9-10) fitted; M1 cap (pins 7-8) removed** -> M1 = 1
   (module pull-up), M0 = 0 = **mode 2** (TBH p.9 mode-2 figure; T37S §6, §7.1). Do **not** follow
   TBH §4 step 2 (both removed = mode 3, no answer).
4. 12 V on the terminal (polarity checked); PWR LED on.
5. USB: TBH-02 into the hub. On the UNO Q: `ls -l /dev/serial/by-id/` and `dmesg | tail` - a CH340
   entry and a `ttyUSB` device (the exact by-id string and the `ch341` driver message are general
   Linux knowledge, not in the sources: VERIFY on the UNO Q image).
6. From `<App>/python`:
   `python3 -m dssq.radio.e22 --port <port> --write --config <App>/data/station.toml`
   (`e22.py:21-22`; App path as in `docs/00:648-649`, VERIFY on the UNO Q). The tool uses `C0`
   (saved, survives power-off, T37S §1.2) unless `--volatile` (`e22.py:406, 431`).
7. Expect `model: E22-400T37S`, `product info: ...`, `written.`, and in the table `uart_bps 9600`,
   `air_rate 2.4k`, `channel 23`, `freq_mhz 433.125`, `rssi_byte True`, `rssi_noise_enable True`,
   `fault_log True`, `fault_log_supported True`, `power_dbm 37.0` (`e22.py:101-121, 416-439`).
   `no reply` = not in mode 2 / no 12 V / caps / port (`e22.py:426`).
8. G-A: refit the M1 cap (mode 0). G-B: remove the M0 cap as well, then wire the RCU (7.2).
9. Set `[gds] rcu`, start the App.

Never run step 6 with both mode caps fitted: in mode 0 the command octets are transmitted on air
(T37S §6.2; `docs/12:912`).

### 7.4 RCU electrical notes (G-B)

* Same levels as the spacecraft: 3.3 V logic both sides (T37S §2.2, UNOQ §9.6). D3 = PB0 is TT,
  3.6 V max (UNOQ §9.6): pull-up to 3.3 V only.
* Before the station sketch runs, the pull-ups hold mode 3 (sleep); `setup()` drives M0/M1 LOW =
  mode 0 (`sketch.ino:1427-1431`).
* Optional protection against a forgotten cap: 1 kOhm in series with each of M0/M1 between the
  UNO Q pin and the header, the 10 kOhm pull-up on the header side. LOW at the module is then
  about 3.3 x 1 / 11 = 0.30 V; the module's VIL is not published (not found) - VERIFY the mode
  switch works (section 12). Recommendation, not from a source.
* `rcu_mode_exec` does not wait for AUX before switching (`sketch.ino:219-225`); harmless, because
  the module defers a switch until AUX is high (T37S §6.1) and the GDS settles 50 ms after each
  switch (`radioctl.py:35, 79-82`), above the 2 ms of T37S §5.6.4 note 3.

### 7.5 Power and sequencing at the ground

* TBH-02: its own regulated 12 V adapter >= 1.5 A (a 12 V / 2 A adapter), 2 A fuse; never from
  the hub or a UNO Q pin (`docs/03:258-261`; T37S §2.2).
* Apply the TBH-02's 12 V **before or together with** the UNO Q: whether the CH340X enumerates on
  USB power alone is not documented (not found); `E22Serial` refuses to start on a missing port
  (`e22.py:316-317`), later losses are re-opened every 2 s (`e22.py:318-320, 345-355`).
* Ground loops: the USB cable already joins the TBH-02 GND to the UNO Q; in G-B add the header GND
  wire next to the M0/M1/AUX wires (`docs/03:604`). Mains adapters with isolated outputs do not
  form a loop.
* Keep the TBH-02 and its antenna feeder away from the hub and chargers (switching noise raises
  the measured noise floor; check with the station noise register / `GSCAN`) - general practice.

### 7.6 Checks at the ground

* G-B: event `ground E22-400T37S: ch 23 (433.125 MHz) rate 2.4k ... - matches station.toml`
  (`docs/03:589-591`).
* G-A: no read-back; the station hears the spacecraft (`STATUS` lines, `sync=LOCK`).
* Dashboard: no YELLOW `radio model mismatch` (`docs/13:1005`); `Fault log` = yes for the station
  model (`docs/13:998`).
* A station abnormal state shows as RED `ground radio fault: <text>` (`docs/14:684`;
  `gds.py:668-678`).

## 9 Range note (the owner's "ultra long range" goal)

From the datasheets: T37S transmits 4 dB more than the T33D (37 vs 33 dBm) but is 2 dB less
sensitive (-126 vs -128 dBm typ at 2.4 kbit/s) (T37S §2.2; T33D §2.2; `docs/02:522`).

| Combination | Downlink vs T33D/T33D | Uplink vs T33D/T33D |
|---|---|---|
| Spacecraft T37S, ground T33D | **+4 dB** | -2 dB |
| Spacecraft T37S, ground T37S | +2 dB | +2 dB |
| Spacecraft T33D, ground T37S | -2 dB | +4 dB |

For the downlink, the best E22 pairing is a T37S on the spacecraft with the more sensitive T33D
at the ground; on air the two models are compatible (`docs/14:105`). The 2.4 kbit/s floor is the
same for both (T37S §7.2); larger range steps come from antenna gain and the SX126x option
(`README.md:57`), outside this report.

## 10 Cross-constraints with the other v4 changes

1. **PB10/PB11 (header "SDA"/"SCL", JDIGITAL 17/18) are the E22 UART on the spacecraft**
   (`config.h:54-63`); `Wire` (I2C2) shares them and is never started (`docs/03:140-144`). The new
   separate Nicla / RM3100 buses (owner item 3) must not use the header SDA/SCL pins; free I2C
   buses are A4/A5 (`Wire2`, I2C3) and the Qwiic socket (`Wire1`, I2C4, PD12/PD13)
   (`docs/03:133-136, 175-176`).
2. **A0 (PA4) is the model strap** (`config.h:107`). A new pin plan that needs A0 must move the
   strap and update `config.h`, docs/03 4.5, docs/00 Part 13, docs/15, FAQ.
3. D2, D3, D7 are the spacecraft's E22 control pins (`config.h:90-92`); the SX126x option uses
   D4-D13 (`docs/03:174`).
4. Ground UNO Q: the RCU pins (proposed D2/D3/D4) and the station's other I/O must not collide;
   if the station keeps a buzzer on A0, the "never strap A0 on the ground" warning stays, with a
   UNO Q reason.
